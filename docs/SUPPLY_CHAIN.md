# Supply chain: dependency risk records

One row per direct dependency (`[workspace.dependencies]` in the root `Cargo.toml`): what the crate can do
inside Ferrofin, what untrusted input reaches it, how well it is maintained, and which audit, if any, covers the
version in `Cargo.lock`. The records are grouped by exposure into three sections: the network and TLS path, the
parsers of untrusted media and files, and the native-code, build-time, WASM-runtime and remaining dependencies.
Every direct dependency has a row in one of them.

The rows are facts read from tools and from the published source, dated below. They are not audits. An audit is
a `cargo-vet` entry (`gates/supply-chain/`; [CONTRIBUTING.md](../CONTRIBUTING.md), "Dependencies", "Audits
(cargo-vet)"), and the last column says which one covers each crate.

## How to read a row

| Column | Meaning |
|---|---|
| Locked | The version in `Cargo.lock` for the dependency Ferrofin declares. A second locked version of the same crate (for example `tower-http` 0.6.11, `tokio-tungstenite` 0.29.0 or `rand` 0.9.5) belongs to a transitive dependency and has no row, and neither does a crate Ferrofin does not declare; where one matters, a section's notes describe it (`rustls-webpki`, the AWS-LC crates). |
| Unsafe code | Number of `unsafe` tokens on non-comment lines of the crate's `src/`, and where. It counts every target (Windows and macOS code included) and every feature, so it is an upper bound for a Linux build with the features Ferrofin enables; a cell says so when a feature Ferrofin leaves off, or another platform, gates the code. "No" means none. A crate that forbids or denies `unsafe_code` says so. |
| Native / C code | C or assembly built or linked into the shipped binary below this crate (`cargo tree -p ferrofin-server -e normal,build`). "FFI declarations only" means it calls the operating system through `libc` or `windows-sys` and ships no C source. |
| Build script | Whether the crate has its own `build.rs`, and what it does. A dependency's build script is not counted. |
| Proc macro | Proc-macro crates in the crate's dependency tree as built into `ferrofin-server`. "Directly" means a dependency of the crate itself; the others sit further down the tree, and some come in only through another crate's feature (for example `serde_derive` below `tokio`, through `smallvec`'s `serde` feature). Only `async-trait` is itself a proc-macro crate, and its row says so. The dev-only rows list the test build of a crate that has them as a dev-dependency instead (`ferrofin-extensions` for `rcgen`, `ferrofin-api` for `tokio-tungstenite`, `ferrofin-server` for `clap_mangen`, `ferrofin-wasm` for `wat`, `ferrofin-util` for `rstest`). |
| Untrusted input | What reaches the crate in Ferrofin: client HTTP, media files, remote metadata, plugins, or none. |
| Maintenance | Whether the locked version is the latest release (`cargo upgrade --dry-run --incompatible allow`, and the crates.io index, because `cargo upgrade` lists only a requirement it would raise and so passes over a newer release the requirement already allows), the publish date of the matching GitHub release in parentheses where the upstream makes one, when the upstream repository was last pushed to, and whether it is archived (GitHub). The dates of each section's run are in Evidence. A push date is repo-wide: where several crates share a repository it is the latest push to any of them. |
| RustSec | Every advisory in the RustSec database filed against the crate, and whether the locked version has the fix. After it, any advisory GitHub holds that RustSec does not carry (GitHub's advisory database and the upstream repository's own security advisories), named by its GHSA id. |
| cargo-crev | The result of `cargo crev crate verify` (cargo-crev 0.27.1): N/A on every row but one. The environment this was run in had no trusted reviewer, so crev prints "There are no trusted Ids. There is nothing to verify against." and shows no review counts. `icu_collator` shows `local`: it is a path dependency (`vendor/icu_collator`), which crev does not verify. The workspace-wide table leaves out the dev-only crates (`rcgen`, `tokio-tungstenite` 0.30.0, `clap_mangen`, `wat`, `rstest`); run on them by name it gives the same result. Ferrofin publishes no crev proofs and gates nothing on crev. |
| Audit | `Imported` names the organisation whose `cargo-vet` audit chain covers the locked version (`cargo vet explain-audit`); a wildcard audit vouches for every version one crates.io publisher releases between two dates. `Exempted, not audited` means the version sits under `[[exemptions]]` in `gates/supply-chain/config.toml`: no organisation Ferrofin imports has audited it and Ferrofin has written no audit of its own. Where imported audits cover only an earlier version or a weaker criterion, the cell says so (`cargo vet suggest`, and the audits the organisations publish). |

An exemption leaves `gates/supply-chain/config.toml` when an imported audit covers the version: run `cargo vet` without
`--locked` to fetch the imports again, then `cargo vet prune`. Ferrofin imports the Bytecode Alliance, Embark
Studios, Google, ISRG, Mozilla and Zcash. The `cargo-vet` public registry also lists Actix, Ariel OS and Fermyon;
none of the three audits a crate with a row here at any version, apart from two Ariel OS deltas (`futures-core` and
`futures-util`, 0.3.31 to 0.3.32), which stop short of the locked 0.3.34, and Fermyon's audits of `anyhow` up to
1.0.68 (locked: 1.0.104). On 2026-11-09, for the parser section and again for the third, fetching the imports again
and pruning, on a copy of the store, retired no exemption.

## Evidence

The network and TLS rows were read on 2026-11-08, and the parser rows and the native-code, build-time, WASM-runtime
and remaining rows on 2026-11-09, each against the locked versions (the network crates' locked versions are the same
on both dates). On 2026-11-09 the network rows' latest-release status and advisories were checked again with the
parser rows' method: they still hold, and only `opentelemetry_sdk` gained an entry (a GitHub advisory RustSec does
not carry). On 2026-11-10 the v1.5.1 freeze sweep moved `uuid`, `crc32fast`, `fancy-regex`, `notify` and `zip` to
new releases, and their rows were read again that day by the same method: each published source matches its
recorded commit (`notify` again publishes its repository's root `README.md`), and no advisory names the new
versions, in the advisory database `cargo-deny` fetched that day or in GitHub's advisory database read that day.

- **Published source against upstream.** For each crate, the commit recorded in its `.cargo_vcs_info.json` was
  fetched from the upstream repository and compared with the published source (`src/`, `build.rs`, tests, benches,
  examples). Nothing differs and nothing exists only in the published crate, apart from cargo's own `.cargo-ok`
  marker and the cases named here. Among the network crates, three were published from a dirty working tree, and in
  each case only the manifest differs from the commit: `http-body` 1.1.0 (the committed manifest still says 1.0.1),
  and `percent-encoding` 2.3.2 and `form_urlencoded` 1.2.2 (the category `no-std` against the committed `no_std`).
  Among the parsers, `lofty` and `notify` publish their repository's root `README.md` (identical to it), and
  `kamadak-exif` 0.6.2 records a commit its GitHub repository does not have: its source is identical to the
  repository's `0.6.2` tag, and only the manifest differs (the tag's package is named `exif`; the published one is
  `kamadak-exif`, with the library still named `exif`). In the third section, `tracing` 0.1.44 contains a
  `test-macros/` folder that its recorded commit lacks: 48 test files marked as generated and a shell script,
  matching an open upstream pull request that generates macro tests. No target in its manifest refers to the folder,
  so nothing of it is built. `tikv-jemalloc-sys` 0.7.1 and `tikv-jemallocator` 0.7.0 were published from a dirty
  tree in which only the manifest differs (the version raised from the committed 0.7.0, and a dev-dependency
  commented out); the jemalloc source is identical to jemalloc's `5.3.1` tag, the submodule commit. `aws-lc-sys`
  0.47.0's AWS-LC source is identical to AWS-LC's `v5.12.0` tag, also a submodule. The `sqlx` 0.9.0 crates ship the
  symbolic links in their folders as plain files holding the link's target, so the licence files of `sqlx-core`,
  `sqlx-sqlite`, `sqlx-macros` and `sqlx-macros-core` contain `../LICENSE-MIT` and `../LICENSE-APACHE` rather than
  the licence text. `libsqlite3-sys` and `clap_mangen` publish files their repository links from its root (identical
  to them). `vendor/icu_collator` was compared with crates.io's `icu_collator` 2.4.0 package and that package with
  its upstream commit (see the third section's notes). This catches code that exists only on crates.io. It does not
  say the upstream commit is benign.
- **Unsafe code.** Counted from the published source with comments and string literals left out.
- **Build scripts, proc macros, native code.** Read from the published `Cargo.toml` and `build.rs`, and from the
  full dependency tree of the shipped binary (`cargo tree -p ferrofin-server -e normal,build --target
  x86_64-unknown-linux-gnu --no-dedupe`), so they describe what Ferrofin builds for Linux on x86-64. Other
  release targets add platform crates that this scan did not walk; the `windows-sys` row was read from its source
  and from Ferrofin's `cfg(windows)` code. The dev-only crates come from the same command run for the crate whose
  tests use them, with `-e normal,build,dev`. Which code a feature or platform leaves out was read from the
  crate's `cfg` attributes and the features `cargo tree -e features` shows enabled.
- **Sinks.** A pattern scan (regular expressions over each crate's `src/` and `build.rs`) mapped where the source
  touches the filesystem, processes, the environment, FFI, `include!` and unchecked-memory primitives. It is a map
  for reading, not a review; the rows name the hits that matter for what the crate is for.
- **RustSec.** Read from the advisory database `cargo-deny` and `cargo-audit` use: the advisory-db commit of
  2026-11-06 for the network rows, of 2026-11-09 for the parser rows, the network re-check and the third section.
  An advisory that
  names an old version range is listed with the first fixed version. GitHub's advisories were read on 2026-11-09
  from its advisory database (`gh api /advisories`, Rust ecosystem) and from each upstream repository's security
  advisories; an advisory RustSec already carries, under its own id or as an alias, is not repeated.
- **Maintenance.** `cargo upgrade --dry-run --incompatible allow`, then the crates.io index for every row.
- **Audits.** `cargo vet explain-audit` for the imported ones; `cargo vet suggest`, and the `audits.toml` each
  organisation in the `cargo-vet` registry publishes, for how close imported audits come to an exempted version.

### Notes on the network and TLS rows

- **Two WebSocket stacks.** `axum` builds its WebSocket support on `tokio-tungstenite` 0.29.0 and `tungstenite`
  0.29, which ship in the binary and are transitive. Ferrofin's own `tokio-tungstenite` 0.30.0 is a
  dev-dependency, so its row is about the test client, not the shipped server.
- **The certificate verifier.** `rustls` verifies through `rustls-webpki`, a transitive dependency. The locked
  0.103.16 is the first release with the fix for RUSTSEC-2026-0382 (distrusted intermediates accepted), and 0.103.10
  to 0.103.13 carry the earlier 2026 fixes. The crate stays covered by the exemption list in `gates/supply-chain/`, not
  by a row here.
- **Native code.** The only separately built C or assembly in this group is AWS-LC (`aws-lc-sys` 0.47.0, the
  AWS-LC source vendored in the crate and built by its build script). In the shipped binary it sits below
  `rustls`, `tokio-rustls`, `reqwest`, `ldap3` and `opentelemetry-otlp`; `rcgen` links it in tests. `x509-parser`
  does not link it in any build, although `Cargo.lock` lists the edge. `ring` is the same case: it is in
  `Cargo.lock` but is not compiled, and `cargo tree -i ring` prints nothing for the workspace.
- **Unsafe in `base64`.** The unsafe code is the SIMD engine module. It is compiled in but unreferenced in the
  shipped tree, so none of Ferrofin's base64 decoding of untrusted input reaches it today.
- **The four imported audits.** `futures-core`, `percent-encoding` and `form_urlencoded` are chains from a full
  audit of an earlier version through delta audits up to the locked one; `httpdate` is a full audit of exactly
  1.0.3. `cargo vet explain-audit <crate> <version>` prints each chain.
- **No real problem found.** Nothing in these rows needed an issue: every locked version carries the fixes for
  the advisories filed against it, and no published source differs from its upstream commit.

### Notes on the parser rows

- **Where the parsing happens.** `image` decodes through `zune-jpeg` (79 `unsafe` tokens, SIMD) and through
  `png`, `gif` and `image-webp`, which forbid unsafe code. `flate2` inflates through `zlib-rs` (453).
  `sevenz-rust2` decodes through `lzma-rust2` (14), `ppmd-rust` (forbids unsafe code) and `bzip2` (18) with
  `libbz2-rs-sys` (132). These are transitive crates, covered by the exemption list in `gates/supply-chain/`,
  not by rows here.
- **The only C in this group** is libwebp, below `webp`, and Ferrofin uses only its lossy encoder: WebP input is
  decoded by `image-webp`, so libwebp's decoder is linked but never called. The vendored copy is a snapshot from
  2023-09. libwebp 1.4.0 (2024-04), 1.5.0 (2024-12) and 1.6.0 (2025-06) have shipped since, and their release
  notes list security hardening and fuzzer fixes but name no CVE. `webp` 0.3.1 cannot take a `libwebp-sys` that
  vendors them.
- **The three imported audits** are wildcard audits that Mozilla publishes, written by the crate's own author or
  maintainer (`encoding_rs` and `chardetng` by their author, `unicode-normalization` by its maintainer). They
  cover every version that publisher releases until the end date, so they say who published the code, not that
  someone else reviewed it.
- **Publisher trust.** For 11 of the exempted crates, `cargo vet suggest` notes that organisations Ferrofin
  imports have trust entries for the crate's publisher: `serde`, `serde_json` and `serde_path_to_error`; `regex`;
  `toml_edit` and `config`; `indexmap`; `tar`; `chrono`; `notify`; and `flate2` (for the publisher of an earlier
  version). `cargo-vet` does not import another organisation's trust entries. Short of an imported audit, only a
  `cargo vet trust` entry in Ferrofin's own `audits.toml` would retire these exemptions, and Ferrofin records none.
- **Moved at the freeze.** `zip` 9.5.0, `uuid` 1.29.2 and `notify` 8.2.2 came out on 2026-11-08 and 2026-11-09,
  after the versions this section had locked, and `fancy-regex` 0.20.1 and `crc32fast` 1.5.5 followed the
  2026-11-09 read. None fixes a security problem. The v1.5.1 freeze sweep (2026-11-10) moved all five, with their
  exemptions, and read their rows again (Evidence).
- **Advisories outside RustSec.** `zip`, `tar`, `sevenz-rust2` and `kamadak-exif` have GitHub advisories RustSec
  does not carry, most of them published in the upstream repository only. Every locked version has their fixes.
- **One problem found:** the vendored libwebp below `webp` (see its row); it is tracked for a fix. Nothing else in
  these rows needed an issue: every locked version carries the fixes for the advisories filed against it, and no
  published source differs from its upstream commit or tag.

### Notes on the native-code, build-time, WASM-runtime and remaining rows

- **Every direct dependency now has a row.** Crates below these rows have none (see Locked): `tikv-jemalloc-sys` is
  described in `tikv-jemallocator`'s row, `sqlx-core`, `sqlx-sqlite`, `sqlx-macros` and `sqlx-macros-core` in
  `sqlx`'s, and the AWS-LC crates in the next note. All of them stay under `[[exemptions]]` at their locked
  versions.
- **AWS-LC.** `aws-lc-rs` 1.19.0 and `aws-lc-sys` 0.47.0, the crypto provider below `rustls`, are transitive.
  `aws-lc-sys` vendors AWS-LC 5.12.0 (C and assembly; identical to AWS-LC's `v5.12.0` tag) and compiles it with
  `cc`; its `src/` holds generated bindings (11,254 `unsafe` tokens in 15 files, nearly all in the per-target
  binding files: 846 in the x86-64 Linux one), and `aws-lc-rs` has 381 in 49 files, its calls into AWS-LC. The
  `prebuilt-nasm` feature is on: a Windows x86-64 build without NASM links 26 pre-assembled `.obj` files shipped in
  the crate (identical to the upstream repository's); the Linux build assembles from source. Five RustSec advisories
  of March 2026 against `aws-lc-sys` were fixed by 0.39.0, so the locked version has their fixes. AWS-LC 5.13.0
  (2026-11-06) is newer; no `aws-lc-sys` release bundles it yet. No imported audit covers either crate at any
  version.
- **The vendored `icu_collator`.** `vendor/icu_collator` is crates.io's `icu_collator` 2.4.0, which is identical to
  the ICU4X commit it records, with one change: `src/elements.rs` takes the shared root Jamo shortcut only for an
  untailored Jamo, so a tailoring's own data (Korean search collation) keeps its expansions and prefixes (five
  lines; `vendor/icu_collator/PATCHED.md`). Only `src/`, `Cargo.toml` (without the tests, benches and README) and
  `LICENSE` are vendored, and `[patch.crates-io]` puts it in place of the crates.io copy. In
  `gates/supply-chain/config.toml`, `audit-as-crates-io = true` makes `cargo-vet` treat it as crates.io's 2.4.0: the
  exemption is for that version, and an imported audit of crates.io's 2.4.0 would retire it although the patched
  lines differ.
- **The SQLite hold.** `libsqlite3-sys` 0.37.0, which bundles SQLite 3.51.3, is the only locked version in the three
  sections without the fix for an advisory filed against it (RUSTSEC-2026-0459). The fix, 0.39 with SQLite 3.54, is
  out of reach while `sqlx-sqlite` 0.9.0 requires `<0.38.0`. `deny.toml` records why Ferrofin is not exposed (only
  Ferrofin, the operator and administrators write a `-wal` into the data folder) and the condition that lifts the
  hold.
- **The WASM runtime.** `wasmtime` compiles every plugin to native code with Cranelift and runs it in the server's
  process, so the plugin sandbox is `wasmtime`'s. Its 67 advisories, and `wasmtime-wasi`'s 10, are the kinds of bug
  that matter here (sandbox escapes, miscompilations, host panics); the locked 50.0.1 has every fix, four of them
  released on 2026-10-29.
- **The imported audits.** `rand` and `shlex` are chains from an imported full audit through delta audits to the
  locked version. `wasmtime`, `wasmtime-wasi` and `wat` are covered by the Bytecode Alliance's wildcard audits of
  its own publishers: the Bytecode Alliance maintains these crates, so, like the wildcard audits in the parser
  section, they say who published the code, not that someone else reviewed it.
- **Publisher trust.** For 14 of the exempted crates, `cargo vet suggest` notes that organisations Ferrofin imports
  trust the crate's publisher: `anyhow`, `async-trait` and `thiserror`; `clap` and `clap_mangen`; the seven ICU4X
  crates and `zerovec`; and `windows-sys`. For `libc` and `tracing-subscriber` the trusted publisher released an
  earlier version, not the locked one. As in the parser section, `cargo-vet` does not import trust entries, and
  Ferrofin records none.
- **Built for tests only, or not at all.** `rstest`, `wat` and `clap_mangen` are dev-dependencies; `rstest` and
  `clap_mangen` are exempted at `safe-to-run`. `windows-sys` 0.61.2 is built only for Windows. `sqlx-mysql` and
  `sqlx-postgres` (`sqlx`'s other drivers) and `windows-sys` 0.52.0 (required by `ring`) are in `Cargo.lock` and
  under `[[exemptions]]`, but nothing builds them: `cargo tree --workspace -i` prints nothing for them on any
  target.
- **No new problem found.** Apart from the SQLite hold, which is already tracked for a fix, every locked version
  carries the fixes for the advisories filed against it, and nothing that is built differs from its upstream commit
  or tag.
